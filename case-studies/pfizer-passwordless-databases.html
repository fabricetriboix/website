Pfizer: getting rid of database passwords on a Kubernetes data platform

Pfizer runs a number of its data and BI applications on a platform built on EKS and AWS managed services. This case study covers how I moved those applications from database passwords to RDS IAM authentication, in a way that the development teams barely noticed, and how I fixed the platform's logging while I was at it.

Client
Pfizer (US)
Sector
Pharmaceuticals
When
September 2025 to September 2026
Role
Platform consultant, remote
Stack
AWS, EKS, Aurora, RDS IAM authentication, Terraform, FluxCD, Grafana Loki, OpenTelemetry, Python

Situation

The platform team was small compared with the number of development teams depending on it, and day-to-day requests were taking longer to answer than anybody wanted. I was brought in as an additional platform engineer. I made it my business to learn the platform quickly so that I could take some of that load, and then to take ownership of a couple of problems that had been waiting for someone to have the time.

The first was database passwords. The applications connected to their Aurora databases with passwords, and passwords need to be stored somewhere, rotated regularly and distributed to the applications that need them. Every one of those steps is a place where something can go wrong, and a large organisation in a regulated industry does not want to explain to an auditor why a database password has not been rotated since the application was written.

Pfizer wanted the applications to access their databases without passwords at all. AWS supports this through RDS IAM authentication, where the application proves its identity to AWS and gets a short-lived token instead of a password. Turning it on is easy enough; the difficulty is that every application has to be changed to use it, and there were many applications, owned by many teams, none of whom had asked for this.

If the solution required every development team to rewrite how their application connects to its database, it was not going to happen, or it was going to happen slowly and unevenly, and the platform team would have spent the next year chasing teams to make the change. So the real requirement was passwordless database access, with as close to zero changes for the development teams as possible.

What I did

I implemented RDS IAM authentication across the platform and hid the mechanics of obtaining database access behind a sidecar container, which meant very few changes for the applications. To make adoption easy, I also wrote a small reference application that shows how to use the new mechanism end to end, so that a team could look at a working example rather than a document. In my experience, a working example is worth a lot of documentation.

The second piece of work was observability. The platform's logging and alerting had grown organically, and there was room to make it a lot more useful. I defined a standard format for structured logging across the platform, so that logs from different applications can be searched and correlated in the same way. I then deployed Grafana Loki in a high-availability configuration and registered it as a data source in Grafana, and I configured the OpenTelemetry Collector to collect container logs and ship them to Loki. All of this is in infrastructure-as-code, so it can be reviewed and reproduced.

Finally, I onboarded a new team whose job was to use AI to extract insights from data held in Snowflake. I worked out what they needed and created the repositories, permissions and GitHub pipelines. I also spent time explaining how the platform works.

Result

Applications on the platform access their databases without passwords, and the development teams did not have to rewrite their database code. Without the passwordless database work, the platform would have failed an audit; the platform team also has one less thing to rotate.

Logs across the platform now share a common structure and a common home, and can be queried from Grafana next to the metrics. In all, 50 tenant teams got visibility into their own workloads, including traces. The AI team was onboarded in two weeks, against a typical 1–2 months, which is roughly what onboarding should take and often does not.

As for the original reason I was brought in, faster answers to the development teams' day-to-day requests, response time was cut from days to hours across 4 development teams. That was partly because I was there and partly because the platform got easier to operate.

If your applications still connect to databases with passwords, and you are in an industry where somebody eventually asks about rotation, this is a well-bounded piece of work with a clear result. It can be done without a big migration project and without upsetting the development teams.

With hindsight, the sidecar approach is pragmatic and it worked, but a sidecar is one more container per pod, and on a large platform that adds up. If I were doing it again from a blank page, I would look at whether the token handling could live in a shared library or in the connection pooler instead, and pick based on how heterogeneous the applications are. On this platform, with many teams and many languages, the sidecar was the right call; on a platform where everything is written in the same language, a library might be.
