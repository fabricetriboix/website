NatWest Bank: observability you can actually trust, on a multi-tenant platform

NatWest Bank was building the next generation of its multi-tenant platform to run Important Business Services, the regulator's term for the services that must not fail. The platform runs on EKS with a good number of AWS managed services around it, and its tenants are the bank's own application teams. I joined the core platform team to work on tenant isolation and observability; the isolation side has its own write-up (see the per-tenant egress case study). This one covers observability and alerting, which is where I ended up spending most of my time: I took the stack from a proof of concept to a production service, made alerting work for the AWS managed services, made every metric and trace attributable to a tenant and then made sure the telemetry pipeline tells you when it is broken.

Client
NatWest Bank (London, UK)
Sector
Banking
When
December 2024 to September 2025
Role
Platform engineer in the core platform team
Stack
AWS, EKS, Terraform, OpenTelemetry, Amazon Managed Prometheus, Amazon Managed Grafana, CloudWatch

Situation

A platform that runs business-critical services has to be observable, and having Grafana installed is only the start. Concretely, four things needed to be true and were not yet:

  • Grafana existed as a proof of concept, set up by hand. It needed to become a production service that could be rebuilt from code and would not depend on anyone remembering how it was configured.
  • The platform relied on a number of AWS managed services, and all their metrics land in CloudWatch, whether you like it or not. There was no systematic way to alert on them.
  • Metrics and traces were flowing, but they did not carry enough context for a tenant to tell which of their workloads a signal came from. On a multi-tenant platform, a metric you cannot attribute to a tenant is not much use to anyone.
  • Nobody was checking that the telemetry pipeline itself was working. Everybody assumed that if the dashboards showed data, the data was complete.

Installing the tools is the easy part of observability on a multi-tenant platform. The hard part is that the platform team and the tenants need different things from the same data, and that the pipeline sits in the middle of everything, so when it breaks it breaks quietly. A dashboard with a gap in it looks exactly like a dashboard where nothing happened.

There is also the managed services problem. You do not get to choose where AWS sends the metrics for RDS or a load balancer: they go to CloudWatch. If your alerting lives in Prometheus, you either move the metrics or you build alerting in two places, and both have a cost.

What I did

First of all, I turned Grafana into a production service defined in Terraform. I designed, implemented and tested an infrastructure-as-code solution to deploy and configure Amazon Managed Grafana: the workspace itself, the dashboards, the plugins and the data sources. I also wrote the Terraform code for data sources so that CloudWatch Logs and Amazon Managed Prometheus register themselves with Grafana, which makes adding a data source part of deploying the feature it belongs to. The proof of concept became something you can destroy and recreate.

Second, I made alerting work for the AWS managed services. I researched bringing the CloudWatch metrics into Amazon Managed Prometheus, so that all metrics would live in one place, and I advised against CloudWatch Alarms because they would create a second alert path alongside Alertmanager. The Head of Platform chose CloudWatch Alarms anyway, because the alternative would take longer given the time available, and I implemented them. I designed a simple, generic way of defining CloudWatch alarms in Terraform, so that adding an alarm for a new service or a new threshold is a few lines of configuration rather than a new piece of engineering. I tested it on a set of alarms and it worked as intended.

Third, some failures only show up in logs. I proposed to the project manager that we should be able to generate alerts from what the logs say, not only from metrics. I then wrote an Architecture Decision Record laying out a couple of ways to achieve this, with their trade-offs, so that the decision could be made properly rather than by whoever got to it first.

Fourth, I made the telemetry usable by the tenants. For a tenant to make sense of their metrics and traces, the signals need to carry the Kubernetes context they were generated in: namespace, workload and pod. I configured the OpenTelemetry collector agents to extract this metadata and attach it as labels to metrics and traces, using the k8sattributesprocessor component. The tenants found this very useful, and a definite improvement over what was there before.

Finally, I tested the pipeline itself, which is the piece I care most about. I suggested that we continuously test the end-to-end path for telemetry, from an application pod all the way to the metrics being stored in Amazon Managed Prometheus, rather than assume it works because the dashboards are not empty. To that effect, I added OpenTelemetry cron jobs that regularly emit known metrics and traces, and alerts that fire if they do not arrive where they should. It is a small amount of code.

Result

Grafana is a production service defined in code, with dashboards and data sources deployed automatically. Alarms on the AWS managed services are declared in Terraform and reviewed like everything else, and the path from logs to alerts has a written decision behind it. Tenants can look at a metric or a trace and know which of their workloads produced it, and 30 engineers across three tenants were unblocked within one week.

The pipeline health checks proved very useful indeed. Within weeks they detected that the path for metrics and traces was intermittently not working: about 5% of metrics were being silently lost, and the problem had gone undetected for months. Nothing on the dashboards gave this away, because the data that did arrive looked fine. Without the checks, somebody would have discovered the gaps during an incident, which is the worst time to find out that your observability has holes in it.

Most platforms I see have observability tools installed, with either too few or too many generic dashboards found on the internet. The dashboards have data, but nobody can say for certain whether the data is complete, whether the alerts would fire if something went wrong on a managed service or which tenant a given signal belongs to. All of that is fixable, and most of it is a few weeks of focused work rather than a programme.

With hindsight, I would push for centralising all metrics in Amazon Managed Prometheus at the very start of the project, when the cost of doing it is low, rather than accept CloudWatch as a second alerting system. The generic CloudWatch alarms work well and I would build them again, but two alerting systems in parallel add friction, and the earlier that decision is made the cheaper it is. I would also build the pipeline health checks on day one, before anything else; they are cheap, and everything you build on top of the telemetry is only as trustworthy as the pipeline underneath it.
